**gl-autodetect** (approved 2026-10-17 with tasks G1-G4; implemented, see Results). Users: anyone running ARIEL (as a library or from `examples/`) on a machine where the default MuJoCo OpenGL backend is unsuitable: no display, no libEGL, no OSMesa, or a driver that crashes. They run a render or a video example and today get a traceback or a hard crash.

Facts the spec rests on (checked 2026-10-17, mujoco 3.8.0): `MUJOCO_GL` is read when `mujoco` is imported (`mujoco/rendering/classic/gl_context.py`), so it must be set before the first `import mujoco` in the process; it only affects `mujoco.Renderer` (offscreen), not `mujoco.viewer`, which always uses GLFW and needs a display; the only code in `src/` that creates a `Renderer` is `ariel/utils/renderers.py` (3 places), and 7 examples create one directly; `examples/re_book/1_brain_evolution_multithreaded.py` documents a hard crash (access violation in `glfwCreateWindow`) when a Renderer is created in a worker thread, so a failing backend can kill its process and each backend must be probed in its own subprocess. On the development machine all three backends fail at `Renderer` creation (glfw: no display; egl: libEGL missing; osmesa: libOSMesa missing), in 0.2-0.5 s each.

Behaviour:
- A *worker* (`python -m ariel.opengl._gl_probe_worker <backend>`, imports only `mujoco`, never `ariel`) sets `MUJOCO_GL`, builds a tiny model, creates a 64x64 `Renderer`, renders 5 frames and prints one JSON line: ok, mean render time in ms, error text.
- A *manager* (`python -m ariel.opengl.gl_manager`, also callable as a function) runs one worker subprocess per backend valid for the platform (Linux: glfw, egl, osmesa; macOS, Windows: glfw only), with a timeout (30 s per backend), records a crash (non-zero or negative exit code), a timeout or an error as `ok: false` with the reason, and writes `mujoco_user_config.json` in the current working directory (atomic write, lock file against parallel writers). A rich progress bar shows the probe and says it is a one-off.
- Config content: `version`, `platform`, `python`, `mujoco` version, `backends` (per backend: `ok`, `render_ms` or null, `error` or null), `selected` (the working backend with the lowest `render_ms`, ties glfw, egl, osmesa; null if none), `viewer_available` (true if glfw works, i.e. a display exists).
- `import ariel` reads the file if present and, only if `MUJOCO_GL` is unset and `mujoco` is not yet imported, sets `MUJOCO_GL` to `selected`. It never probes and never raises: a missing, unreadable or corrupt file is a warning (corrupt) or nothing (missing).
- Importing a module that needs OpenGL (today `ariel.utils.renderers`; a public `ariel.opengl.gl_backend.ensure_gl_backend()` for user scripts) probes automatically when the file is missing, with the progress bar and a one-off message, then applies the result if `mujoco` is not yet imported (otherwise it says the choice takes effect on the next run). Two processes starting at once probe once (lock).
- The config is also refreshed when the recorded `mujoco` version or platform differs from the running one, and on request: `python -m ariel.opengl.gl_manager`.
- An existing `MUJOCO_GL` in the environment always wins and is never overwritten.

Acceptance criteria (each a test):
1. Running the manager in a temporary folder writes a valid file (all keys above, correct types); on a machine where nothing works, `selected` is null and `viewer_available` false, the manager exits 0.
2. A worker that crashes (simulated with a fake backend that aborts) or hangs past the timeout is recorded `ok: false` with a reason, the other backends are still probed, and the manager exits 0.
3. With a config whose `selected` is `osmesa` and `MUJOCO_GL` unset, a fresh `python -c "import ariel, os; print(os.environ.get('MUJOCO_GL'))"` prints `osmesa`; with `MUJOCO_GL=egl` preset it prints `egl`; with `selected: null` it prints `None`; with a corrupt file it prints a warning and does not raise.
4. Importing `ariel.utils.renderers` with no file probes exactly once and creates the file; a second import in the same folder does not start a subprocess.
5. Two processes importing at the same moment produce one file and one probe run.
6. A read-only working directory only warns; ARIEL still imports.
7. `pytest tests/unit` passes with the new tests (no real GL needed: workers are faked), `ruff check`, `ruff format --check` and `mypy` stay at zero, coverage stays at least 54%.
8. `.gitignore` lists `mujoco_user_config.json`; the README has a short note (what the file is, how to regenerate, that `MUJOCO_GL` wins).
Not verified here (needs another machine): a run where at least one backend works, and Windows/macOS.

Non-goals: changing the interactive viewer; switching backend while a process runs; fixing examples that import `mujoco` before `ariel` (they keep the default backend and only get a hint); GPU selection or a real benchmark (one small render per backend is the speed measure); setting `PYOPENGL_PLATFORM` (MuJoCo does it for egl itself); a setting to turn the probe off.

Integration points: `src/ariel/__init__.py` (reads config, already sets global state), new `src/ariel/opengl/gl_backend.py` (first written as `utils/gl_backend.py`, moved by R2d-1) (read/apply/ensure, imports no mujoco), `gl_manager.py`, `_gl_probe_worker.py`; `src/ariel/utils/renderers.py` (calls `ensure_gl_backend()` before `import mujoco`, with an isort split and an E402 note); tests under `tests/unit/test_utils/`; `.gitignore`; README. `rich` is already a dependency, so no new dependency. The import-direction rule holds: `utils` imports nothing from the other packages.

Architecture and alternatives:
- Chosen: subprocess-per-backend probe plus a JSON file in the user's working folder, read at `import ariel`, auto-probe on first import of a GL-needing module.
- Rejected: probing in-process (a glfw crash kills the caller, as the multithreaded example documents); documenting `MUJOCO_GL` only (leaves the crash for every new user); config under `~/.config/ariel/` (user preferred the working folder for library use; cost: a new folder re-probes once); probing on every `import ariel` (seconds of delay in every worker process); two modes `view`/`batch` (the viewer ignores `MUJOCO_GL`, so the second mode would change nothing).
- Consequence of the cwd choice: the file belongs to the machine, not the folder, so each new working folder probes once.

Open ambiguities: (a) the staleness rule above (mujoco version or platform change) does not notice a driver change; the manual command covers that; (b) the 30 s timeout and 5-frame, 64x64 measure are my picks; (c) when `mujoco` is already imported at probe time the choice only applies on the next run.

**no-overlap** (goal and tasks O1-O6 approved 2026-10-19).

- Users: anyone who turns a graph into a robot with `construct_mjspec_from_graph` (the CPPN, probability, vector and tree decoders, the examples) and wants a body whose modules do not sit inside each other.
- Interface: `construct_mjspec_from_graph(graph, *, repair_overlaps=False)`. With the default nothing changes. With `True` the function returns the body of `repair_overlaps(graph)`, a new function in a new module `src/ariel/body_phenotypes/robogen_lite/overlap.py`, exported from `ariel.body_phenotypes`; it takes a `DiGraph` and returns a pruned copy (the argument is never changed).
- Geometry, read from the evidence (a 4-module body compiled 2026-10-19): every module geom in robogen-lite is a MuJoCo box (core half-size 0.1 m, brick 0.05 m, hinge stator 0.0248 x 0.0297 x 0.0248 and rotor 0.025 x 0.02 x 0.025), and a geom is named `<parent>-<child>-<face>-<kind>` (the core's geom is `core`), so the second number is the node it belongs to. A hinge has two geoms (stator, rotor), both owned by the hinge node. Any other geom type raises `ValueError` (none exists today).
- One round: build the body from the graph, compile it, run `mj_forward` for the world pose of every geom, make one Trimesh box per geom (extents twice the half-sizes, transform from the pose), put them in a `trimesh.collision.CollisionManager`, and ask for every colliding pair with contact data. A pair of geoms counts only when their owner nodes differ and are not parent and child in the graph. Its penetration depth is the largest depth among its contacts.
- Tolerance, per pair: the size of a module is the total volume of its geoms and its thinnest side is twice the smallest half-size of its geoms; the pair overlaps when `depth > 0.01 * thinnest side of the smaller module`. The ratio 0.01 is a named constant. Computed from the real sizes on every call, so scaling a body does not change the verdict.
- Later module of a violating pair: the one with more edges from the core; at equal depth, walk both paths from the core to the first edge where they differ and take the one whose face comes later in FRONT, BACK, RIGHT, LEFT, TOP, BOTTOM. The core is never removed (it is on every path, so it can never be the deeper of a pair).
- Loop: collect the violating pairs, take the one whose later module is deepest (ties: the smaller node id), remove that module with its whole subtree, log one debug line (`pruned 3 modules (ids 7, 9, 12) for overlap with 4`), and run a new round. Deepest first removes the least. It ends when a round finds no violating pair; every round removes at least one module, so it ends after at most as many rounds as there are modules.
- Not changed: poses at joint angle zero only; the decoders' own placement (`cppn_best_first` keeps its occupied-cell grid); genomes (the pruning acts on the graph made for one robot, the genome keeps its genes).
- Non-goals: overlap that appears when joints move; mesh or non-box geoms; regrowing pruned modules elsewhere; repair at genome level; turning the repair on by default or in the decoders; changing physics or module sizes; the `hardware` branch.
- Acceptance criteria and the test or measurement for each: (1) 0 of 60 bodies per source with a self-contact deeper than the tolerance after repair, counted by MuJoCo's `mj_geomDistance`, not Trimesh (`tools/measure_overlap.py`, new, one command, seed 42; before the change the same tool must print today's counts); (2) a body without overlap gives byte-identical XML with the flag on and off (unit test on fixed graphs, plus the same check over the 180 bodies in the tool); (3) the later-module rule, the tolerance rule (a pair just under and just over 1%, the same pair scaled by 2) and the parent-child exemption each have a unit test on hand-built graphs; (4) the repair never changes its argument and always ends (unit tests); (5) repair time per body measured and recorded in DESIGN.md Results (target 20 ms, building a body takes 4 to 7 ms; not a pass or fail); (6) pytest coverage 100%, ruff, mypy unchanged in count.
- Integration points and conventions to follow: `construct_mjspec_from_graph` in `robogen_lite/constructor.py` (97 lines; its 9 `# type: ignore[...]  # known bug` lines stay as they are); top-level package entry `ariel.body_phenotypes` re-exports the public name (CLAUDE.md import rule); only `overlap.py` imports `trimesh`; pydantic frozen models for records (`FrozenModel` from `ariel.parameters`), no `dataclass`; tests may import any module.
- Risks: python-fcl's penetration depth for box against box may differ from MuJoCo's (the check in criterion 1 is independent on purpose; if they disagree by more than the tolerance the task stops and asks); FCL is not installed yet, so its behaviour is untested until task O1; hinge geoms at a rotation might need a tolerance different from the bricks.

**speed-up** (spec of Phase 0, 2026-10-20; the goal is in PLAN.md). Metric: wall-clock time of four workloads, median of 10 runs with the spread (largest minus smallest); CPU time and peak memory are printed beside it, not judged. `uv run --no-sync python tools/benchmark.py [WORKLOAD ...] [--runs N]`, workloads `evolution`, `simulation`, `bodies`, `tests`, each run in a fresh process (`--once NAME` prints one JSON line `{wall, cpu, rss}`). `evolution`: a seeded tree-genome evolution, population 20, 10 generations (`EVO_POP`, `EVO_STEPS`), trees of up to 15 modules, each new robot built with `construct_mjspec_from_graph` and simulated 1000 steps (2.5 s of robot time) in `SimpleFlatWorld` with a sine control on every actuator, fitness the forward (x) distance of the first body, maximised; parent selection marks the better half, reproduction adds 20 children (a coin flip between a copy and `crossover_subtree`, then `mutate_replace_node` or `mutate_subtree_replacement`, then `prune_invalid_edges`), survivor selection keeps the 20 best; the database is in a temporary folder and the EA is quiet. `simulation`: the prebuilt `john_set.gecko_small()` (named `john_set.gecko` until 2026-10-21) in `SimpleFlatWorld` for 100000 steps with the same sine control (5000 steps took 0.24 s, too short to time). `bodies`: 60 random trees of 20 modules built plain, then the same 60 with `repair_overlaps=True`. `tests`: `uv run --no-sync pytest -q -p no:cacheprovider` in a child process, with the coverage run the gate uses. Peak memory is `ru_maxrss` of the process (of the children for `tests`). All seeds are 42, so the work is the same in every run. No code outside `tools/` and its tests is touched by the benchmark.

**geometry-measures** (spec approved by the user 2026-10-21; the goal is in PLAN.md). `MorphologicalMeasures(robot)` takes the `CoreModule` from `construct_mjspec_from_graph` (or a prebuilt robot) and measures that body; there is no graph argument. Example: `robot = construct_mjspec_from_graph(graph, repair_overlaps=True)`, then `MorphologicalMeasures(robot).bounding_box_depth` is a length in metres.
- Definitions: axes are the core's own frame (depth along FRONT to BACK, width LEFT to RIGHT, height TOP to BOTTOM); pose at joint angle zero, as compiled (as `overlap.py`); a module's size is the summed volume of its box geoms and its position the volume-weighted centre of them; the bounding box is the extent of all geoms along the three axes in metres, `bounding_box_volume` their product; `coverage` and `size` are the summed module volumes over the bounding box volume (0 to 1); `proportion` and `proportion_2d` are min(depth, width) / max(depth, width); `is_2d` means no module reaches above or below the core; symmetry per plane through the core's centre: a module is on the plane when its centre is within half its thinnest side of it, an off-plane module is mirrored when a module of the same type sits at its mirror point within half the smaller of the two thinnest sides, the score is mirrored over off-plane modules (0 when none is off the plane), and `symmetry` is the best of the three planes; every count (joints, limbs, branching, filled modules and the rest) keeps its definition and reads the graph the body was built from.
- Architecture: `CoreModule.graph` (the graph the body was built from, or `None`) is set by `construct_mjspec_from_graph` (a copy of the graph, the pruned one when `repair_overlaps=True`) and by every prebuilt builder through `prebuilt_robots/parts.attach`, which attaches a module and records it in one call (the 13 `john_set` tables through `parts.build`, and the hand-written `gecko`, `spider`, `random_spider20`, `body_spider`, `body_spider45`, user's choice 2026-10-21; `rotation` holds degrees there, since counts never read it); `MorphologicalMeasures` raises `ValueError` when it is `None`. Every graph node records the name prefix of its module's geoms, so each geom has one owner; the constructor's names (`<parent>-<node>-<face>-...`) and the prebuilt names (`hinge_0...`) stay as they are, because other code may look parts up by name. `robogen_lite/rest_pose.rest_boxes` compiles a body and returns each geom's owner (longest matching prefix, else the core), half sizes and pose in the core's frame (so `body_spider45`, whose core is turned, measures like `body_spider`); `overlap.find_overlaps` and the measures are its two users; `overlap.owner_of` (regex on the constructor's names) stays for the `overlap_repair` notebook. The core's frame: FRONT along +y (depth), RIGHT along +x (width), TOP along +z (height); the core's centre is at y = 0.1 m. `morphological_grid.py` is deleted; its graph helpers and the edge-face check move into `morphological_counts.py`; `morphological_descriptor.py` computes the geometry measures.
- Must not regress: every count gives today's value on the same graph (golden values for 60 random bodies, seed 42, and the 17 prebuilt robots, recorded before the change); simulation, the constructor's output for a graph, the prebuilt robots' geom names and the overlap repair do not change.
- Acceptance criteria: the seven in the goal row in PLAN.md.
- Non-goals: comparability with Miras 2018 or revolve2; measures of a moving robot; new measures; a speed budget (time per body recorded only).

**servo-dynamics.** Goal and spec approved 2026-10-22 (the user's answers that day; the goal and its measured acceptance tests are in PLAN.md Goals). - Numbers (from `ariel.parameters.DSSM15`, rating at 6 V): stall torque 13.5 kgf cm = 1.324 N m; no-load speed 0.18 s per 60 degrees = 5.82 rad/s; travel 180 degrees; gear 310:1.
- Actuator: a position servo (MuJoCo `position`-style affine actuator, control = target angle) with `forcerange` plus or minus the stall torque; kp = stall torque / 5 degrees = 15.2 N m/rad (full torque at 5 degrees of error, like a hobby servo that holds firmly); kv chosen for critical damping of the hinge's inertia (rotor plus armature), counted inside the torque cap.
- Joint: `range` plus or minus 90 degrees with `limited`; damping = stall torque / no-load speed = 0.228 N m s/rad, which is a DC motor's straight torque-speed line: under its own power the hinge tops out at 5.8 rad/s, and an outside torque assisting it pushes it to 5.8 + torque / 0.228 rad/s, as back-EMF braking would on the real motor; armature = rotor inertia of a comparable small DC motor times 310 squared, stored as an astropy quantity marked as an estimate: SD1 chose the maxon A-max 16, part 110079 (0.816 g cm2, read from maxongroup.com 2026-10-22), whose stall torque of 4.49 mN m becomes 1.39 N m after the 310:1 gear, close to the DSS-M15's 1.32 N m; armature 0.00784 kg m2, about 55 times the rotor's own inertia. Mabuchi publishes no rotor inertias, and the A-max 22 variants (3.9 to 4.4 g cm2) would give 0.04 kg m2: a time constant (armature over damping) of 0.18 s, as long as the datasheet's whole 60-degree move, which the measured sweep in acceptance 2 (0.54 to 0.65 s for 180 degrees) would not allow.
- Where values live: `DSSM15` keeps the datasheet; a small frozen servo-settings record (voltage 6 V, holding error 5 degrees, the armature estimate and its source) sits beside it in `ariel.parameters` and in `ArielModulesConfig`; `hinge.py` derives kp, kv, damping, range and forcerange from them and writes no number of its own.

## Decisions

Stack and architecture as found in the repo. Reasons are not recorded unless stated.

- Python ≥ 3.12 with uv for environments and dependencies (`uv.lock`); setuptools build backend (`nox` and the opt-in mypyc `setup.py` were removed on 2026-10-21). Reason: the README names uv; no other reason recorded.
- Simulation on MuJoCo (`mujoco`); bodies are built as MuJoCo `MjSpec` objects. Reason not recorded. (`mujoco-mjx[warp]` and `dm-control` were declared until 2026-10-20 but nothing imported them; see the dependency clean-up below.)
- Evolution engine in `ariel.ec`: `EA` with operations over a `Population` of `Individual`s stored with SQLModel/SQLAlchemy (database-backed, with restart from the database and an `Archive`). Reason not recorded.
- Body encodings: RoboGen-lite modular robots (`Core`, `Brick`, `Hinge`) decoded from genotypes (tree, CPPN-NEAT, NDE in PyTorch, vectors). The Lynx arm is a separate body family.
- Controllers are CPG-based (five models in `simulation/controllers/cpg/`, see the cpg-variants decision below), and tasks are free-function fitness functions.
- Optimisation libraries available: Nevergrad, plus an in-repo `RevDE`. EvoTorch left with Ray in goal parallelism P5 (2026-10-23); DEAP, listed here before, is not a dependency (not in `pyproject.toml` or `uv.lock`).
- Dashboards (Plotly/Panel) live on the `feature-dashboard` branch, not on `main`; `main` has no plotting dependencies.
- Typing and docs: strict ruff (`ALL`), strict mypy and pyright, NumPy docstrings, 100% coverage target. Free functions are preferred over classes (`.claude/dev/functional_vs_oo.md`); records are pydantic models, see the global-standard decision below.

- NA-CPG (`simulation/controllers/na_cpg.py`, since 2026-10-21 `simulation/controllers/cpg/na_cpg.py`), re-implemented 2026-10-18 from Tong et al., "NA-CPG: A robust and stable rhythm generator for robot motion control", Biomimetic Intelligence and Robotics 2 (2022) 100075, equations 2 to 12, because three diverging files had left the meaning unclear. The old code differed from the paper in four ways that changed the output: the amplitude term was `alpha (1 - r^2)^2` where the paper has `alpha (1 - r^2)`; `r^2` ignored the offset `b` (paper: `x^2 + (y - b)^2`); the state buffer `xy_dot_old` held the previous state, not the previous derivative that `zeta` and the constraint need; the constraint was a fixed clamp of 10. Also missing were the coupling coefficient `h` and the offset in the coupling term. Kept from the old files: the five parameter groups (`phase`, `w`, `amplitudes`, `ha`, `b`), `BetaParams`-sampled initial values (now per instance, seeded, with ranges bounded to physical values), `angle_limits` with `clipping` and `clamping_error` (mean distance to the limits), the setters, `save`/`load`. Dropped: the `normalize` option and `duration` of `na_cpg_norm.py`, which are not in the paper (there "normalized" means the amplitude is fixed to 1 and `theta_i = A_i y_i`), and the class that could not be imported. The update is vectorised over the oscillators (paper section 2.3). Start state: each oscillator on its limit cycle at its own phase, `(cos phi_i, sin phi_i + b_i)`, derivative zero, so coupled oscillators start phase locked; `reset_state()` recomputes it from the current parameters. The constraint function: the paper fits `CF(w)` to the largest second derivative per angular frequency and does not publish the fit, so the default is `CF(w) = CONSTRAINT_MARGIN * w^2 * dt` (the largest change of the derivative per step on the unit circle, margin 3 covers `ha` up to about 0.4); a cubic can still be set through the attribute `coefficients` (the old research notebook `tests/functional/cpg.ipynb` did; deleted 2026-10-22) (highest power first). Defaults follow the paper: `alpha = 30`, `dt = 0.01`, `ha = 0.4` as the asymmetric example. Measured with the tests: amplitude within 2 % of the set value for a single oscillator and a 4-chain (paper: 5.3 %), a share of 0.32 of the period below zero for `ha = 0.4` (theory 0.30).

- CPG package (cpg-variants, 2026-10-21, the user's choices): `simulation/controllers/cpg/` holds five models (seven with Tegotae, below) on one abstract base `CPG` (an `nn.Module`): `HopfCPG` and `AdaptiveHopfCPG` (Righetti and Ijspeert, ICRA 2006, eq. 1-3), `PhaseCPG` (Ijspeert 2007, CPG-RL 2022, Raj and Kos 2026 eq. 1-2), `SwingStanceCPG` (Righetti and Ijspeert, ICRA 2008, eq. 1-5) and `NaCPG` (moved, maths unchanged). `SimpleCPG` was deleted, not fixed: it added `phase` to the joint angle as a constant (so with its default ranges 46% of samples sat at the joint limit), its diffusive coupling could not hold a phase difference, and its ranges let `w` and the amplitude go negative; its four examples now use `HopfCPG` (genome of 4 groups instead of 5, `ha` dropped, `b` became `offset`). The clock: `forward(time)` integrates over the time since the last timed call in equal sub-steps of at most `dt`, because `Controller` calls the callback only every `time_steps_per_ctrl_step` physics steps (0.125 s by default) and the old fixed 0.01 s per call made every CPG run 12.5 times slow inside a simulation (measured on the gecko: 1 Hz asked, 0.08 Hz seen). The first timed call and a time earlier than the last one reset the state; `forward()` with no time keeps the old one-step behaviour. NA-CPG's constraint scales with the sub-step (`CF = 3 w^2 step`). Choices made here, each recorded because the papers leave them open: phase targets are per joint (`phase_i`), and every model couples pairs to `phase_i - phase_j`, so a model has `n` parameters per group, not `n^2`; `SwingStanceCPG` turns the paper's +1/-1 gait matrices into `k_ij = h cos(phase_i - phase_j)`, which reproduces them but holds only in-phase and anti-phase pairs; `AdaptiveHopfCPG` keeps only the frequency adaptation of the 2006 paper (eq. 1-3), because the full teaching-signal network needs a recorded gait, and takes its input from `set_input`; the touch-sensor feedback of the 2008 paper is left out because the modules have no foot sensors. Coupling strengths default to 1 in every model and are not searched by the locomotion notebook. Tegotae (added the same day, the user's choices): `TegotaeCPG` is the fixed rule `dphi/dt = w - sigma N cos(phi)` with `sigma` per joint, and `LearnableTegotaeCPG` the paper's generalisation (Herneth, Hayashibe and Owaki, ICRA 2023), with `A'`, `R` and `G` as one-hidden-layer tanh networks shared by every joint (51 weights at `hidden=4`; the paper found PGPE could not train more than 128). Both output `offset + A cos(phi)` (the user chose this over the paper's reflex actuation, eq. 7, which only pushes while touch disagrees and so leaves a hinge still on flat ground); `A` ranges over plus and minus pi/2 because the sign picks which half of the swing is stance. `R(N) - R(0)` is used so that a limb with no load gets no feedback, as in the fixed rule; the paper does not say. The oscillators are not wired to each other (`coupling = 0`), as in the papers. The load is the vertical floor force on every body the joint moves, computed in `cpg_locomotion` from MuJoCo contacts (on the resting gecko it sums to the robot's weight, 22.5 N); it stays out of the library because only that notebook needs it. The paper PDF was read with a stdlib text extractor in the scratchpad (no `pdftoppm` here). The locomotion search starts CMA-ES from each CPG's seeded random parameters, not the middle of the unit cube, because the middle of the symmetric Tegotae amplitude range is a gecko that does not move (2 trials: 0.002 m against 0.05 m for the others). Best gaits are kept (2026-10-22, the user's choice after a run that kept none): `cpg_locomotion` writes each CPG's best parameters, its seed and distance as `best_<CPG>.json` (a `BestGait` pydantic model) and films the best gait as `best_<CPG>_<time stamp>.mp4` in `__data__/cpg_locomotion/` under the folder the notebook runs in, git-ignored like every run output, showing only one frame of each inline (at 50 dpi) to stay under the 500 KB notebook limit. `tools/run_notebooks.py` runs every notebook in a temporary folder and deletes it, which is right for a test but threw the first run's videos away; to keep them, run it in place: `cd tests/functional && uv run --no-sync jupyter execute --inplace cpg_locomotion.ipynb`. It films inside its own `trial` loop (one frame every 9 physics steps, a camera tracking the core at 0.9 m) rather than with `tracking_video_renderer`, so the video is the scored trial itself (the check asserts the filmed distance equals the scored one) and the Tegotae loads still arrive after every step; without a working OpenGL backend it saves the JSON, skips the videos and runs every check. The papers: `tests/functional/cpg_properties.ipynb` lists them; the arXiv 2211.00458 and NA-CPG PDFs could not be read here (no `pdftoppm`), so the phase model follows the review and Raj and Kos.

- `VectorDecoder.vectors_to_graph` (2026-10-18), direct decoding: each vector holds one value in [0, 1] per module except the core (`num_modules - 1`). Module `k` takes its type from `type_vector[k - 1]` (BRICK, HINGE, NONE; NONE is left out), its parent and face from `connection_vector[k - 1]` (one free `(parent, face)` slot of the modules placed before it, so the graph is a tree by construction and there is always a slot: the core has 4 faces and every placed module offers at least as many as it uses), and its rotation from `rotation_vector[k - 1]` among the rotations its type allows (`ALLOWED_ROTATIONS`). - mujoco-units seeds (`simulators/mujoco/seeds.py`, MU3, 2026-10-19): `Seeds` is a `FrozenModel`, not a `pydantic_settings.BaseSettings`, because nothing reads seeds from the environment and the global rule shares one base class; each quantity is validated by a `PlainValidator` that needs an astropy `Quantity` of the right dimension, a scalar, positive and finite, and stores it in one canonical unit (m, m/s, rad/s, m/s^2, kg/m^3, Pa s), so later formulas read plain SI numbers; `1/s` counts as `rad/s` (astropy `dimensionless_angles`). `Seeds.replace(**changes)` re-validates (`model_copy(update=...)` does not, see Gotchas). `joint_frequency` default 100 rad/s (about 16 Hz, a stiff hobby servo; judgement, the user asked for the seed on 2026-10-19 without a value; 200 rad/s was tried and made `gamma / omega_max` equal to the advection limit, 2.5 ms, so the binding term flipped on rounding); standard gravity is the plain number 9.80665 because `astropy.constants.g0` and `astropy.units.g0` are invisible to mypy. astropy ships no type hints, so the one call to `Quantity.to` sits in `_to` with a single `# type: ignore[no-untyped-call]`.

- mujoco-units settings (`simulators/mujoco/settings.py`, MU5, 2026-10-19): a setting is a path into `mujoco.MjSpec` (`option.timestep`, `visual.global_.offwidth`, `default.geom.solref`) with a kind (`seed`, `formula`, `fixed`), a reason and a source. - mujoco-units MJCF (`simulators/mujoco/mjcf.py`, MU7, 2026-10-19): `build_spec` sets every setting on a fresh `MjSpec` by its path; `generate_xml` is `spec.to_xml()` plus one attribute. Found by testing: `MjSpec.to_xml` writes only values that differ from the engine defaults (so the file is the list of differences, 21 of 156 with the default seeds (10 when MU7 was written), and every other value is the installed engine's default) and never writes `compiler.balanceinertia`; `generate_xml` adds `balanceinertia` by string insertion so a reload gives back every setting (a test reads the loaded file with `read_spec` and compares all 156). Consequence for the goal text 'one MJCF that holds all values': the file holds the differences; the full table is printed by `python -m ariel.simulators.mujoco` and, from MU9, written to `docs/source/mujoco_parameters.md`. - How the inputs are built (cpg-steering, 2026-10-22): an `InputRoute(handle, joint)` per entry of `u`. A route with a joint passes the value as it is to that joint; a route without one sends it to every joint times a weight per joint, the rows of the group `input_weights` (bounds -1 to 1, last in `get_flat_params`, present only when such a route exists). Reason: sensor values are per joint and already have a gain in the model (`sigma` for Tegotae, `epsilon` for `AdaptiveHopfCPG`), so a second weight would only duplicate it, while a steering feature is one number every joint must answer to differently; this is the plan's default "each feature drives one handle per joint" (8 x m on the gecko), and a feature that should drive two handles is given twice in `u`. `amplitude` and `frequency` multiply by `1 + d` clamped at 0, `offset` adds `d` radians: a factor keeps the sign of Tegotae's negative amplitudes and a weight range of -1 to 1 that means the same for every model, while an offset is already in radians. `NaCPG`'s offset input moves the centre `b` of its cycle, as its own offset does, so its output glides to the new offset. - Mirroring modules (measured 2026-10-23 for goal sims-genotype, by building each pair in MuJoCo and comparing geom corners and joint axes after a mirror through the plane x = 0). Face names are local to each module, named looking outward from its parent: a brick on the core's RIGHT face has its RIGHT face pointing backward (-y), and one on the core's LEFT face has its RIGHT face pointing forward (+y). A brick's cross-section is square, so a brick at +45 degrees has the same shape as one at -45; its mirror image is the same tilt with the faces below it renamed: at 0 degrees LEFT and RIGHT swap, at 45 TOP and LEFT swap and BOTTOM and RIGHT swap, at 90 TOP and BOTTOM swap (error under 0.1 mm in every case). - How unfolding mirrors a subtree (goal sims-genotype G3, 2026-10-23). Each placed module carries a reflection R, in its own frame, with mirror(module) = twin composed with R. For a child on face f with tilt t, the twin child goes on the face f' and tilt t' where the site position R p(f) equals p(f') and the relation (A(f') T(t'))^T R A(f) T(t) is one of the child's own reflective symmetries (A: the site's frame, T: the module's tilted frame, both read from `CoreModule`, `BrickModule` and `HingeModule`); that symmetry is the child's R. A brick has four (planes through its growth axis: across x, across z and the two diagonals, its cross-section being square); a hinge has two (across x and across z), because its joint axis must stay on its own line. The core's R is the reflection between its LEFT and RIGHT sites. A module lies on the centre plane when its own face and tilt solve this for the parent's R; only there does a mirror flag add a twin. Search order is the original tilt first, then 0, 45, 90, and -45 for a hinge only, so a brick keeps its tilt and a 45-degree hinge's twin is at -45. ## Gotchas

- `ensure_gl_backend()` is not a test of whether OpenGL works: it returns `None` whenever `MUJOCO_GL` is already set, and the first `import ariel.rendering` sets it, so a second call returns `None` on a machine where rendering works (found 2026-10-22 in `cpg_locomotion`, which then skipped its videos). After `import ariel.rendering`, `os.environ.get("MUJOCO_GL")` is the answer: the probe sets it only to a backend that rendered a frame (`apply_config`), and a user's preset wins.

- CPG state tensors (`xy`, `theta`, `r`, `frequency`, ...) are made inside `torch.inference_mode()` (in `CPG.forward`), so changing one in place outside it (`cpg.r *= 0.2`) raises "Inplace update to inference tensor outside InferenceMode is not allowed".
