**gl-autodetect** (approved 2026-10-17 with tasks G1-G4; implemented, see Results). Users: anyone running ARIEL (as a library or from `examples/`) on a machine where the default MuJoCo OpenGL backend is unsuitable: no display, no libEGL, no OSMesa, or a driver that crashes. They run a render or a video example and today get a traceback or a hard crash.

Facts the spec rests on (checked 2026-10-17, mujoco 3.8.0): `MUJOCO_GL` is read when `mujoco` is imported (`mujoco/rendering/classic/gl_context.py`), so it must be set before the first `import mujoco` in the process; it only affects `mujoco.Renderer` (offscreen), not `mujoco.viewer`, which always uses GLFW and needs a display; the only code in `src/` that creates a `Renderer` is `ariel/utils/renderers.py` (3 places), and 7 examples create one directly; `examples/re_book/1_brain_evolution_multithreaded.py` documents a hard crash (access violation in `glfwCreateWindow`) when a Renderer is created in a worker thread, so a failing backend can kill its process and each backend must be probed in its own subprocess. On the development machine all three backends fail at `Renderer` creation (glfw: no display; egl: libEGL missing; osmesa: libOSMesa missing), in 0.2-0.5 s each.

Behaviour:
- A *worker* (`python -m ariel.opengl._gl_probe_worker <backend>`, imports only `mujoco`, never `ariel`) sets `MUJOCO_GL`, builds a tiny model, creates a 64x64 `Renderer`, renders 5 frames and prints one JSON line: ok, mean render time in ms, error text.
- A *manager* (`python -m ariel.opengl.gl_manager`, also callable as a function) runs one worker subprocess per backend valid for the platform (Linux: glfw, egl, osmesa; macOS, Windows: glfw only), with a timeout (30 s per backend), records a crash (non-zero or negative exit code), a timeout or an error as `ok: false` with the reason, and writes `mujoco_user_config.json` in the current working directory (atomic write, lock file against parallel writers). A rich progress bar shows the probe and says it is a one-off.
- Config content: `version`, `platform`, `python`, `mujoco` version, `backends` (per backend: `ok`, `render_ms` or null, `error` or null), `selected` (the working backend with the lowest `render_ms`, ties glfw, egl, osmesa; null if none), `viewer_available` (true if glfw works, i.e. a display exists).
- `import ariel` reads the file if present and, only if `MUJOCO_GL` is unset and `mujoco` is not yet imported, sets `MUJOCO_GL` to `selected`. It never probes and never raises: a missing, unreadable or corrupt file is a warning (corrupt) or nothing (missing).
- Importing a module that needs OpenGL (today `ariel.utils.renderers`; a public `ariel.opengl.gl_backend.ensure_gl_backend()` for user scripts) probes automatically when the file is missing, with the progress bar and a one-off message, then applies the result if `mujoco` is not yet imported (otherwise it says the choice takes effect on the next run). Two processes starting at once probe once (lock).
- The config is also refreshed when the recorded `mujoco` version or platform differs from the running one, and on request: `python -m ariel.opengl.gl_manager`.
- An existing `MUJOCO_GL` in the environment always wins and is never overwritten.

Acceptance criteria (each a test):
1. Running the manager in a temporary folder writes a valid file (all keys above, correct types); on a machine where nothing works, `selected` is null and `viewer_available` false, the manager exits 0.
2. A worker that crashes (simulated with a fake backend that aborts) or hangs past the timeout is recorded `ok: false` with a reason, the other backends are still probed, and the manager exits 0.
3. With a config whose `selected` is `osmesa` and `MUJOCO_GL` unset, a fresh `python -c "import ariel, os; print(os.environ.get('MUJOCO_GL'))"` prints `osmesa`; with `MUJOCO_GL=egl` preset it prints `egl`; with `selected: null` it prints `None`; with a corrupt file it prints a warning and does not raise.
4. Importing `ariel.utils.renderers` with no file probes exactly once and creates the file; a second import in the same folder does not start a subprocess.
5. Two processes importing at the same moment produce one file and one probe run.
6. A read-only working directory only warns; ARIEL still imports.
7. `pytest tests/unit` passes with the new tests (no real GL needed: workers are faked), `ruff check`, `ruff format --check` and `mypy` stay at zero, coverage stays at least 54%.
8. `.gitignore` lists `mujoco_user_config.json`; the README has a short note (what the file is, how to regenerate, that `MUJOCO_GL` wins).
Not verified here (needs another machine): a run where at least one backend works, and Windows/macOS.

Non-goals: changing the interactive viewer; switching backend while a process runs; fixing examples that import `mujoco` before `ariel` (they keep the default backend and only get a hint); GPU selection or a real benchmark (one small render per backend is the speed measure); setting `PYOPENGL_PLATFORM` (MuJoCo does it for egl itself); a setting to turn the probe off.

Integration points: `src/ariel/__init__.py` (reads config, already sets global state), new `src/ariel/opengl/gl_backend.py` (first written as `utils/gl_backend.py`, moved by R2d-1) (read/apply/ensure, imports no mujoco), `gl_manager.py`, `_gl_probe_worker.py`; `src/ariel/utils/renderers.py` (calls `ensure_gl_backend()` before `import mujoco`, with an isort split and an E402 note); tests under `tests/unit/test_utils/`; `.gitignore`; README. `rich` is already a dependency, so no new dependency. The import-direction rule holds: `utils` imports nothing from the other packages.

Architecture and alternatives:
- Chosen: subprocess-per-backend probe plus a JSON file in the user's working folder, read at `import ariel`, auto-probe on first import of a GL-needing module.
- Rejected: probing in-process (a glfw crash kills the caller, as the multithreaded example documents); documenting `MUJOCO_GL` only (leaves the crash for every new user); config under `~/.config/ariel/` (user preferred the working folder for library use; cost: a new folder re-probes once); probing on every `import ariel` (seconds of delay in every worker process); two modes `view`/`batch` (the viewer ignores `MUJOCO_GL`, so the second mode would change nothing).
- Consequence of the cwd choice: the file belongs to the machine, not the folder, so each new working folder probes once.

Open ambiguities: (a) the staleness rule above (mujoco version or platform change) does not notice a driver change; the manual command covers that; (b) the 30 s timeout and 5-frame, 64x64 measure are my picks; (c) when `mujoco` is already imported at probe time the choice only applies on the next run.

**no-overlap** (goal and tasks O1-O6 approved 2026-10-19).

- Users: anyone who turns a graph into a robot with `construct_mjspec_from_graph` (the CPPN, probability, vector and tree decoders, the examples) and wants a body whose modules do not sit inside each other.
- Interface: `construct_mjspec_from_graph(graph, *, repair_overlaps=False)`. With the default nothing changes. With `True` the function returns the body of `repair_overlaps(graph)`, a new function in a new module `src/ariel/body_phenotypes/robogen_lite/overlap.py`, exported from `ariel.body_phenotypes`; it takes a `DiGraph` and returns a pruned copy (the argument is never changed).
- Geometry, read from the evidence (a 4-module body compiled 2026-10-19): every module geom in robogen-lite is a MuJoCo box (core half-size 0.1 m, brick 0.05 m, hinge stator 0.0248 x 0.0297 x 0.0248 and rotor 0.025 x 0.02 x 0.025), and a geom is named `<parent>-<child>-<face>-<kind>` (the core's geom is `core`), so the second number is the node it belongs to. A hinge has two geoms (stator, rotor), both owned by the hinge node. Any other geom type raises `ValueError` (none exists today).
- One round: build the body from the graph, compile it, run `mj_forward` for the world pose of every geom, make one Trimesh box per geom (extents twice the half-sizes, transform from the pose), put them in a `trimesh.collision.CollisionManager`, and ask for every colliding pair with contact data. A pair of geoms counts only when their owner nodes differ and are not parent and child in the graph. Its penetration depth is the largest depth among its contacts.
- Tolerance, per pair: the size of a module is the total volume of its geoms and its thinnest side is twice the smallest half-size of its geoms; the pair overlaps when `depth > 0.01 * thinnest side of the smaller module`. The ratio 0.01 is a named constant. Computed from the real sizes on every call, so scaling a body does not change the verdict.
- Later module of a violating pair: the one with more edges from the core; at equal depth, walk both paths from the core to the first edge where they differ and take the one whose face comes later in FRONT, BACK, RIGHT, LEFT, TOP, BOTTOM. The core is never removed (it is on every path, so it can never be the deeper of a pair).
- Loop: collect the violating pairs, take the one whose later module is deepest (ties: the smaller node id), remove that module with its whole subtree, log one debug line (`pruned 3 modules (ids 7, 9, 12) for overlap with 4`), and run a new round. Deepest first removes the least. It ends when a round finds no violating pair; every round removes at least one module, so it ends after at most as many rounds as there are modules.
- Not changed: poses at joint angle zero only; the decoders' own placement (`cppn_best_first` keeps its occupied-cell grid); genomes (the pruning acts on the graph made for one robot, the genome keeps its genes).
- Non-goals: overlap that appears when joints move; mesh or non-box geoms; regrowing pruned modules elsewhere; repair at genome level; turning the repair on by default or in the decoders; changing physics or module sizes; the `hardware` branch.
- Acceptance criteria and the test or measurement for each: (1) 0 of 60 bodies per source with a self-contact deeper than the tolerance after repair, counted by MuJoCo's `mj_geomDistance`, not Trimesh (`tools/measure_overlap.py`, new, one command, seed 42; before the change the same tool must print today's counts); (2) a body without overlap gives byte-identical XML with the flag on and off (unit test on fixed graphs, plus the same check over the 180 bodies in the tool); (3) the later-module rule, the tolerance rule (a pair just under and just over 1%, the same pair scaled by 2) and the parent-child exemption each have a unit test on hand-built graphs; (4) the repair never changes its argument and always ends (unit tests); (5) repair time per body measured and recorded in DESIGN.md Results (target 20 ms, building a body takes 4 to 7 ms; not a pass or fail); (6) pytest coverage 100%, ruff, mypy unchanged in count.
- Integration points and conventions to follow: `construct_mjspec_from_graph` in `robogen_lite/constructor.py` (97 lines; its 9 `# type: ignore[...]  # known bug` lines stay as they are); top-level package entry `ariel.body_phenotypes` re-exports the public name (CLAUDE.md import rule); only `overlap.py` imports `trimesh`; pydantic frozen models for records (`FrozenModel` from `ariel.parameters`), no `dataclass`; tests may import any module.
- Risks: python-fcl's penetration depth for box against box may differ from MuJoCo's (the check in criterion 1 is independent on purpose; if they disagree by more than the tolerance the task stops and asks); FCL is not installed yet, so its behaviour is untested until task O1; hinge geoms at a rotation might need a tolerance different from the bricks.

**speed-up** (spec of Phase 0, 2026-10-20; the goal is in PLAN.md). Metric: wall-clock time of four workloads, median of 10 runs with the spread (largest minus smallest); CPU time and peak memory are printed beside it, not judged. `uv run --no-sync python tools/benchmark.py [WORKLOAD ...] [--runs N]`, workloads `evolution`, `simulation`, `bodies`, `tests`, each run in a fresh process (`--once NAME` prints one JSON line `{wall, cpu, rss}`). `evolution`: a seeded tree-genome evolution, population 20, 10 generations (`EVO_POP`, `EVO_STEPS`), trees of up to 15 modules, each new robot built with `construct_mjspec_from_graph` and simulated 1000 steps (2.5 s of robot time) in `SimpleFlatWorld` with a sine control on every actuator, fitness the forward (x) distance of the first body, maximised; parent selection marks the better half, reproduction adds 20 children (a coin flip between a copy and `crossover_subtree`, then `mutate_replace_node` or `mutate_subtree_replacement`, then `prune_invalid_edges`), survivor selection keeps the 20 best; the database is in a temporary folder and the EA is quiet. `simulation`: the prebuilt `john_set.gecko()` in `SimpleFlatWorld` for 100000 steps with the same sine control (5000 steps took 0.24 s, too short to time). `bodies`: 60 random trees of 20 modules built plain, then the same 60 with `repair_overlaps=True`. `tests`: `uv run --no-sync pytest -q -p no:cacheprovider` in a child process, with the coverage run the gate uses. Peak memory is `ru_maxrss` of the process (of the children for `tests`). All seeds are 42, so the work is the same in every run. No code outside `tools/` and its tests is touched by the benchmark.

**geometry-measures** (spec approved by the user 2026-10-21; the goal is in PLAN.md). `MorphologicalMeasures(robot)` takes the `CoreModule` from `construct_mjspec_from_graph` (or a prebuilt robot) and measures that body; there is no graph argument. Example: `robot = construct_mjspec_from_graph(graph, repair_overlaps=True)`, then `MorphologicalMeasures(robot).bounding_box_depth` is a length in metres.
- Definitions: axes are the core's own frame (depth along FRONT to BACK, width LEFT to RIGHT, height TOP to BOTTOM); pose at joint angle zero, as compiled (as `overlap.py`); a module's size is the summed volume of its box geoms and its position the volume-weighted centre of them; the bounding box is the extent of all geoms along the three axes in metres, `bounding_box_volume` their product; `coverage` and `size` are the summed module volumes over the bounding box volume (0 to 1); `proportion` and `proportion_2d` are min(depth, width) / max(depth, width); `is_2d` means no module reaches above or below the core; symmetry per plane through the core's centre: a module is on the plane when its centre is within half its thinnest side of it, an off-plane module is mirrored when a module of the same type sits at its mirror point within half the smaller of the two thinnest sides, the score is mirrored over off-plane modules (0 when none is off the plane), and `symmetry` is the best of the three planes; every count (joints, limbs, branching, filled modules and the rest) keeps its definition and reads the graph the body was built from.
- Architecture: `CoreModule.graph` (the graph the body was built from, or `None`) is set by `construct_mjspec_from_graph` (a copy of the graph, the pruned one when `repair_overlaps=True`) and by every prebuilt builder through `prebuilt_robots/parts.attach`, which attaches a module and records it in one call (the 13 `john_set` tables through `parts.build`, and the hand-written `gecko`, `spider`, `random_spider20`, `body_spider`, `body_spider45`, user's choice 2026-10-21; `rotation` holds degrees there, since counts never read it); `MorphologicalMeasures` raises `ValueError` when it is `None`. Every graph node records the name prefix of its module's geoms, so each geom has one owner; the constructor's names (`<parent>-<node>-<face>-...`) and the prebuilt names (`hinge_0...`) stay as they are, because other code may look parts up by name. `robogen_lite/rest_pose.rest_boxes` compiles a body and returns each geom's owner (longest matching prefix, else the core), half sizes and pose in the core's frame (so `body_spider45`, whose core is turned, measures like `body_spider`); `overlap.find_overlaps` and the measures are its two users; `overlap.owner_of` (regex on the constructor's names) stays for the `overlap_repair` notebook. The core's frame: FRONT along +y (depth), RIGHT along +x (width), TOP along +z (height); the core's centre is at y = 0.1 m. `morphological_grid.py` is deleted; its graph helpers and the edge-face check move into `morphological_counts.py`; `morphological_descriptor.py` computes the geometry measures.
- Must not regress: every count gives today's value on the same graph (golden values for 60 random bodies, seed 42, and the 17 prebuilt robots, recorded before the change); simulation, the constructor's output for a graph, the prebuilt robots' geom names and the overlap repair do not change.
- Acceptance criteria: the seven in the goal row in PLAN.md.
- Non-goals: comparability with Miras 2018 or revolve2; measures of a moving robot; new measures; a speed budget (time per body recorded only).

## Decisions

Stack and architecture as found in the repo. Reasons are not recorded unless stated.

- Python ≥ 3.12 with uv for environments and dependencies (`uv.lock`); setuptools build backend; `nox` for task automation (docs only today). Reason: the README names uv; no other reason recorded.
- Simulation on MuJoCo (`mujoco`); bodies are built as MuJoCo `MjSpec` objects. Reason not recorded. (`mujoco-mjx[warp]` and `dm-control` were declared until 2026-10-20 but nothing imported them; see the dependency clean-up below.)
- Evolution engine in `ariel.ec`: `EA` with operations over a `Population` of `Individual`s stored with SQLModel/SQLAlchemy (database-backed, with restart from the database and an `Archive`). Reason not recorded.
- Body encodings: RoboGen-lite modular robots (`Core`, `Brick`, `Hinge`) decoded from genotypes (tree, CPPN-NEAT, NDE in PyTorch, vectors). The Lynx arm is a separate body family.
- Controllers are CPG-based (`SimpleCPG`, `NaCPG`), and tasks are free-function fitness functions.
- Optimisation libraries available: DEAP, EvoTorch, Nevergrad, plus an in-repo `RevDE`.
- Dashboards (Plotly/Panel) live on the `feature-dashboard` branch, not on `main`; `main` has no plotting dependencies.
- Typing and docs: strict ruff (`ALL`), strict mypy and pyright, NumPy docstrings, 100% coverage target. Free functions are preferred over classes (`.claude/dev/functional_vs_oo.md`); records are pydantic models, see the global-standard decision below.
- Global state at import: `ariel/__init__.py` sets `DATA`, a seeded `RNG` (seed 42) and rich logging. Reason not recorded.

- Image handling: switch `opencv-python` to `opencv-python-headless` (decided 2026-10-17, for goal test-env-green). Reason: `import cv2` fails with `libGL.so.1` missing on machines without that system library, and nothing in `src/` needs a cv2 window. The one live window, in `examples/a_mujoco/3_cameras_in_simulation.py`, moves to matplotlib. Performance hint: if image or camera display ever feels slow, suspect that matplotlib replaced `cv2.imshow`, which is faster for live frames. Implemented in T3 with the version pinned to 4.11.0.86 (the locked opencv-python version; PyPI's newest is a 5.x major). Related to but separate from goal gl-autodetect: cv2 and MuJoCo use different GL paths, so this switch does not settle which `MUJOCO_GL` backend to use.
- gl-autodetect config (decided 2026-10-17, implemented in G1-G4): `mujoco_user_config.json` lives in the user's working directory, not `~/.config`, because ARIEL is used as a library and already keys its outputs to the working directory (`ariel.DATA = cwd/__data__`). Cost: the probe re-runs per working folder although the result depends on the machine, and the file needs a `.gitignore` note. It is regenerated on first run if missing and on request via the manager script; a missing file must never crash import (falls back to MuJoCo's default). The user chose to probe automatically on the first import of a module that needs OpenGL (`ariel.utils.renderers`), with a rich progress bar and a one-off message, not at every `import ariel`, because probing takes seconds and multiprocessing workers also import `ariel`. A preset `MUJOCO_GL` always wins. Linux is tested; macOS and Windows probe `glfw` only and have not been tried.
- Lint/type policy (goal lint-types-policy, decided 2026-10-17 in the config review; implemented in T7-T18): ruff `fix = false`, `unsafe-fixes = false`, lint `preview` off, format `preview` on, ruff pinned to `0.14.*`. Reason (measured): lint preview adds 187 findings from 25 unstable rules, while turning format preview off would make 56 instead of 47 files fail the format check, because the code is already formatted in preview style. Both mypy and pyright are kept (user's choice; pyright to be added to the dev group). Enforcement: add a CI workflow running tests, ruff and mypy, non-blocking until counts reach zero, and fix pre-commit so its tools install from the venv. Outcome: all three reached zero, so those steps are blocking in `.github/workflows/checks.yml`; pyright is informational (`continue-on-error`). pre-commit uses `pre-commit/pre-commit-hooks` v6.0.0 plus local ruff hooks through `uv run --no-sync`.
- Ruff rule policy (decided 2026-10-17, rule-group walkthrough; implemented in T7-T15; the exceptions that were kept are listed in the T15b row). Keep `select = ["ALL"]` with: line length stays 80 and long lines are fixed by hand (E501 239 + W505 95); missing-docstring rules (D100-D107) required in `src/`, ignored in `tests/`; `ANN` required in `src/`, ignored in `tests/`; ERA001 kept (delete the 54 commented-out blocks, they stay in git history); T201 `print` ignored in `examples/` and kept in `src/` (implemented as per-file ignores for `examples/**`, `src/ariel/body_phenotypes/lynx_mjspec/unified_pipeline/**`, `cppn_neat/tests.py` and `simulation/example_usage.py`, plus `PLR0915` for the generated `john_set.py`); COM812 ignored (conflicts with the formatter; ruff's docs advise this); TRY003 ignored, EM101/EM102 kept; `[lint.pylint] max-args = 8`; every other rule (SIM, SLF001, PLC0415, PT011, ARG, ...) kept and fixed, with no test exemptions. Measured with this draft config on 2026-10-17: 976 findings in `src` + `tests` (803 + 173; was 1330), `examples/` 1274 (not in scope: not checked by any command in CLAUDE.md). mypy: `[mypy-quaternion.*]` switches from `follow_untyped_imports` to `ignore_missing_imports`, which takes mypy from 262 to 236 errors.
- Entry point: no console script; `[project.scripts]` is removed rather than adding `ariel.__main__` (decided 2026-10-17). Reason: the user does not want a CLI. Done in T1.
- Dashboards leave `main` for a `feature-dashboard` branch, to be revisited once the core is fixed (decided 2026-10-17; done in T4, T5). Reason: untested, three near-duplicate versions, about 5.5k lines. The branch was cut at `6ab657f` (Merge T3), so it keeps the dashboard dependencies and none of the later lint and type work.
- Wiki sources for MuJoCo come from the Read the Docs `/stable/` docs (the newest release), not `/latest/` (development branch) and not a pinned `/en/3.8.0/`; decided by the user 2026-10-18. Consequence: the docs describe 3.16.0 while `uv.lock` pins 3.8.0, so a page's default can differ from the installed engine; defaults for ARIEL are read from the installed engine (`mjcf_defaults_3_8_0`) and every MuJoCo wiki page carries a version note. Upgrading MuJoCo to match is a separate, approval-needing dependency change (PLAN.md, Known problems).
- `examples/` and `docs/` are excluded from ruff (`ruff.toml` `exclude`) and mypy (`mypy.ini` `exclude`), so the user's global Python gate covers `src`, `tests` and `setup.py`. Decided by the user 2026-10-18 (this is a deliberate narrowing of the gate's scope, asked for and approved, not a loosened rule). - NA-CPG (`simulation/controllers/na_cpg.py`), re-implemented 2026-10-18 from Tong et al., "NA-CPG: A robust and stable rhythm generator for robot motion control", Biomimetic Intelligence and Robotics 2 (2022) 100075, equations 2 to 12, because three diverging files had left the meaning unclear. The old code differed from the paper in four ways that changed the output: the amplitude term was `alpha (1 - r^2)^2` where the paper has `alpha (1 - r^2)`; `r^2` ignored the offset `b` (paper: `x^2 + (y - b)^2`); the state buffer `xy_dot_old` held the previous state, not the previous derivative that `zeta` and the constraint need; the constraint was a fixed clamp of 10. Also missing were the coupling coefficient `h` and the offset in the coupling term. Kept from the old files: the five parameter groups (`phase`, `w`, `amplitudes`, `ha`, `b`), `BetaParams`-sampled initial values (now per instance, seeded, with ranges bounded to physical values), `angle_limits` with `clipping` and `clamping_error` (mean distance to the limits), the setters, `save`/`load`. Dropped: the `normalize` option and `duration` of `na_cpg_norm.py`, which are not in the paper (there "normalized" means the amplitude is fixed to 1 and `theta_i = A_i y_i`), and the class that could not be imported. The update is vectorised over the oscillators (paper section 2.3). Start state: each oscillator on its limit cycle at its own phase, `(cos phi_i, sin phi_i + b_i)`, derivative zero, so coupled oscillators start phase locked; `reset_state()` recomputes it from the current parameters. The constraint function: the paper fits `CF(w)` to the largest second derivative per angular frequency and does not publish the fit, so the default is `CF(w) = CONSTRAINT_MARGIN * w^2 * dt` (the largest change of the derivative per step on the unit circle, margin 3 covers `ha` up to about 0.4); the old research notebook `tests/functional/cpg.ipynb` can still set a cubic through the attribute `coefficients` (highest power first). Defaults follow the paper: `alpha = 30`, `dt = 0.01`, `ha = 0.4` as the asymmetric example. Measured with the tests: amplitude within 2 % of the set value for a single oscillator and a 4-chain (paper: 5.3 %), a share of 0.32 of the period below zero for `ha = 0.4` (theory 0.30).

- `VectorDecoder.vectors_to_graph` (2026-10-18), direct decoding: each vector holds one value in [0, 1] per module except the core (`num_modules - 1`). Module `k` takes its type from `type_vector[k - 1]` (BRICK, HINGE, NONE; NONE is left out), its parent and face from `connection_vector[k - 1]` (one free `(parent, face)` slot of the modules placed before it, so the graph is a tree by construction and there is always a slot: the core has 4 faces and every placed module offers at least as many as it uses), and its rotation from `rotation_vector[k - 1]` among the rotations its type allows (`ALLOWED_ROTATIONS`). Values map through `assign_symbols_from_range`; a slot is chosen by index because that helper treats a list of tuples as per-element symbols. The user asked what the choice changed and did not pick, so this was chosen for them: it matches the unfinished code and needs no invented rule. - mujoco-units seeds (`simulators/mujoco/seeds.py`, MU3, 2026-10-19): `Seeds` is a `FrozenModel`, not a `pydantic_settings.BaseSettings`, because nothing reads seeds from the environment and the global rule shares one base class; each quantity is validated by a `PlainValidator` that needs an astropy `Quantity` of the right dimension, a scalar, positive and finite, and stores it in one canonical unit (m, m/s, rad/s, m/s^2, kg/m^3, Pa s), so later formulas read plain SI numbers; `1/s` counts as `rad/s` (astropy `dimensionless_angles`). `Seeds.replace(**changes)` re-validates (`model_copy(update=...)` does not, see Gotchas). `joint_frequency` default 100 rad/s (about 16 Hz, a stiff hobby servo; judgement, the user asked for the seed on 2026-10-19 without a value; 200 rad/s was tried and made `gamma / omega_max` equal to the advection limit, 2.5 ms, so the binding term flipped on rounding); standard gravity is the plain number 9.80665 because `astropy.constants.g0` and `astropy.units.g0` are invisible to mypy. astropy ships no type hints, so the one call to `Quantity.to` sits in `_to` with a single `# type: ignore[no-untyped-call]`.

- mujoco-units settings (`simulators/mujoco/settings.py`, MU5, 2026-10-19): a setting is a path into `mujoco.MjSpec` (`option.timestep`, `visual.global_.offwidth`, `default.geom.solref`) with a kind (`seed`, `formula`, `fixed`), a reason and a source. Defaults are read from the installed engine by walking the spec objects (`read_object`), not typed in, so an upgrade shows up as a changed default; enums become integers and arrays tuples of floats. Every setting that ARIEL does not override is `fixed` with a per-section reason and source (the XML reference, the wiki page, the installed engine); a reason per attribute would be 157 hand-written sentences with no extra information. Overrides are `option.timestep`, `gravity`, `density`, `viscosity` (seeds and formula), `default.geom.solref` and `friction` (formula and seed), and the four choices ARIEL already made in the old `MujocoConfig` (`integrator` implicitfast, `balanceinertia`, `degree` False, offscreen 960 x 1280). `compiler.eulerseq` (a character vector) and `stat` (compiler output) are left out. `visual.global` is skipped because it is the same object as `visual.global_`.

- mujoco-units MJCF (`simulators/mujoco/mjcf.py`, MU7, 2026-10-19): `build_spec` sets every setting on a fresh `MjSpec` by its path; `generate_xml` is `spec.to_xml()` plus one attribute. Found by testing: `MjSpec.to_xml` writes only values that differ from the engine defaults (so the file is the list of differences, 21 of 156 with the default seeds (10 when MU7 was written), and every other value is the installed engine's default) and never writes `compiler.balanceinertia`; `generate_xml` adds `balanceinertia` by string insertion so a reload gives back every setting (a test reads the loaded file with `read_spec` and compares all 156). Consequence for the goal text 'one MJCF that holds all values': the file holds the differences; the full table is printed by `python -m ariel.simulators.mujoco` and, from MU9, written to `docs/source/mujoco_parameters.md`. Writing every default into the XML by hand was rejected: it needs a mapping of 156 spec names to XML names and keywords (`angle`, `cone`, `<flag>`, `<lengthrange>`) with no test that the mapping is right, for a file the engine reads the same either way. `compiler.authored` (a bit mask the XML parser sets) is not a setting and is skipped. The risk of implicit defaults (a future MuJoCo changing one) is covered by the MU9 test, which fails when the regenerated table differs from the document.

## Gotchas

- `EA(restart=path)` copies the alive individuals of the last generation into a **new** database at `db_file_path` (or `config.db_file_path`); it does not append to the source file, so give the restarted run its own path (found 2026-10-19 while writing `ec_engine.ipynb`).
- nbclient raises `CellExecutionError` before the failing cell's error output is stored, so `tools/run_notebooks.py` finds the failing cell as the last one with an execution count.

See "Things that bite" in CLAUDE.md for repo-wide ones. Design-specific ones:

- Band edges need a tolerance. With the default seeds the timestep is advection-limited, so `courant = h * v_max / L` equals `alpha` (0.05) up to rounding (0.05000000000000001), which is the upper edge of its band; `simulators/mujoco/bands.py` compares edges with a relative tolerance of 1e-9. Likewise a default that ties two limits of the timestep flips the binding term on rounding (`joint_frequency` 200 rad/s tied with the advection limit and was changed to 100).

- `HighProbabilityDecoder` and `Blueprint` use attributes they never define; `OlympicArena` cannot be instantiated (abstract `_expand_spec`, a misspelling of `_extend_spec`); `SimpleTiltedWorld` reads `_terrain_color`, which is never set. These are the `# known bug` ignores listed in PLAN.md.
- `mujoco.viewer` (used by about 20 examples) always uses GLFW and ignores `MUJOCO_GL`; only `mujoco.Renderer` honours it. A GLFW `Renderer` created in a worker thread crashes (`examples/re_book/1_brain_evolution_multithreaded.py` documents an access violation in `glfwCreateWindow`), which is why every backend is probed in its own subprocess.
- The 3 `# noqa: E712` comments in `ec/archive.py` and 1 in `ec/ea.py` are needed: SQLAlchemy columns must be compared with `== False`.
- `test_all_heightmap_functions` (`tests/unit/test_simulation/test_environments/test_environments.py`) inspects the namespace of `simulation/environments/heightmap_functions.py`, so that module uses `typing.cast` and must not import `cast` as a name.
- `opencv-python-headless` has no windows: `cv2.imshow` does not work. If camera or image display ever feels slow, suspect that `examples/a_mujoco/3_cameras_in_simulation.py` now uses matplotlib instead of `cv2.imshow` (that example was never run, there is no display on the development machine).
- A one-line docstring that does not fit in 80 columns cannot satisfy both E501 and D200 (`D212` is ignored in `ruff.toml`), so T12 shortened such summaries until they fit on one line.
- `ruff format` also formats the notebooks under `tests/functional/` (cell source only); pre-commit's ruff hooks only look at `src/` and `tests/`, while docs and examples keep about 1,270 findings.
- Importing `ariel.utils.renderers` in a folder without `mujoco_user_config.json` runs a probe of a few seconds and writes the file into that folder; `tests/conftest.py` presets `MUJOCO_GL=glfw` so the test suite never does this in the repository.
- `uv run --no-sync pyright` downloads Node and the pyright npm package into `~/.cache/pyright-python` (229 MB) on its first run.
- The MuJoCo docs at `/stable/` describe 3.16.0 (changelog of 2026-10-14) and this repo has 3.16.0 installed since 2026-10-19 (MU1); the wiki page `mjcf_defaults_3_8_0` is the old measurement and `mjcf_defaults_3_16_0` lists what changed. Read defaults from the installed engine, not from the wiki, and fetch versioned pages (`/en/3.16.0/`) when a value must match.
- A callback `Protocol` with `/` before `*args, **kwargs` accepts only callbacks whose first two parameters are positional-only too (otherwise a caller's `**kwargs` could clash with their names): see `ControlCallback`; the test callbacks and `cppn_decoding` use `/`.
- `np.generic` and bare `np.ndarray` count as explicit `Any` for `disallow_any_explicit`; use a concrete dtype (`NDArray[np.float64]`, `np.void` for quaternion arrays). A PEP 695 `type X = NDArray[...]` alias is flagged where a plain annotation is not.
- The probe worker sets `MUJOCO_GL` in the calling process; a test that runs it must restore the variable (`monkeypatch.setenv`), or a later spawned worker that imports mujoco can hang. `mujoco_worker` also sets `OMP_NUM_THREADS` and friends in the caller.
- ruff `--select X --fix` with `RUF100` in the list removes valid `ruff: ignore` comments for rules that were not selected; this cost a revert in GS5. Check with the full rule set.
- Pydantic copies the dicts and lists it validates, so a model built from your own list no longer shares it. `TreeGenome.to_dict()` returns copies, not the live edge list.
- `BaseModel.model_copy(update=...)` does not validate the update, so a frozen settings model copied that way skips its validators and warnings. Re-validate with `Model.model_validate(model.model_dump() | {...})`. Computed fields still recompute on a copy.
- The global command guard (`~/.claude/hooks/python-guard.sh`) refuses a Bash command that contains the text of a pip install even inside a heredoc of page content; reword the text or write the file with the Write tool.
- mypy 1.18.2 stops with `INTERNAL ERROR` (AssertionError in `expand_type`/`visit_param_spec`) on an attribute access through a `ParamSpec`-generic class (`EAOperation[**P]`, `bound.kwargs` in `tests/unit/test_ec/test_ea.py`). After a crash mypy reports only the errors found before it, so the count looks small and grows when the crash is avoided: check that a `mypy .` run ends with `Found N errors` or `Success`, not `INTERNAL ERROR`.
- Coverage can depend on randomness (2026-10-19): `decoders/hi_prob_decoding.py` lines 191-192 (a module whose best type is NONE) were reached only when a test with random probability spaces happened to pick NONE, so 2 of 12 parallel runs fell to 99% and the user's Stop gate reported `pytest` as failed (exit 3). `pytest-cov` then writes its "Coverage failure" message through `terminalreporter.write`, which `pytest-modern`'s `ModernTerminalReporter` lacks, so the run ends in an `INTERNALERROR` that hides the cause. Found by running the suite 12 times in parallel with `COVERAGE_FILE` set per run and reading each with `coverage report --data-file=... --show-missing`. Fixed with a deterministic test (`test_hi_prob_none_module_loses_all_its_connections`). If the gate fails on pytest again, do the same.
- The readthedocs `programming/*.html` pages are prose only; the struct and enum tables of the old wiki pages came from the C headers. The headers of the installed MuJoCo (`.venv/lib/python3.12/site-packages/mujoco/include/mujoco/`) are the free, version-exact source for refreshing those pages.
- After a module re-exports a name through its package `__init__` (restructure R2d), code that imports it from the package holds its own reference: a test that monkeypatches the old module attribute no longer reaches it. Patch the name on the package that the code imports from (`from ariel import rendering`, `monkeypatch.setattr(rendering, "single_frame_renderer", ...)` in `test_cppn_decoding.py`); a miss shows as a real render and an aborted pytest process (exit 134), not as a test failure.
- Top-level packages re-export every part on first import (`ariel.simulation`, `ariel.body_phenotypes`, `ariel.ec`), so `import ariel.simulation` loads MuJoCo and the environments; `ariel.opengl` and `ariel` itself must stay free of MuJoCo (pinned by `tests/unit/test_opengl/test_opengl_entry_point.py`). Import time was not measured.
- `tools/render_floors.py` and `tools/run_notebooks.py` (planned) cannot run on this machine: no OpenGL backend works here. Tests fake the renderer.
- `MUJOCO_GL` order in notebooks: `mujoco` reads it when it loads, so a notebook that imports `mujoco` before `ariel.rendering` keeps MuJoCo's default backend and ariel only prints that its choice applies next time. Put the `from ariel.rendering import ...` cell first (CLAUDE.md code rules; the three older OpenGL notebooks still import `mujoco` first, PLAN.md Known problems).

- MuJoCo contacts cannot count overlaps between robot modules: MuJoCo skips contacts between bodies that are rigidly welded together (no joint between them), which is every brick, and the core, so `d.contact` only shows pairs across a hinge. Use `mujoco.mj_geomDistance(model, data, geom1, geom2, 1.0, fromto)` (negative for a penetration, ignores the filter). It has a blind spot of its own: for a brick rotated 45 degrees whose edge pokes into a neighbour it returned 0.0 where an exact boolean intersection (`trimesh.boolean.intersection`, engine `manifold`) gave 4.3e-5 m3 (4.3% of a brick) and python-fcl gave a depth of 0.0207 m, which is right (one body of 180, tree of 20 modules, seed 42). Found in O3, 2026-10-19, after O2 had counted contacts.
- Benchmarks (found 2026-10-20 while measuring the speed-up baseline): run nothing else while one runs. The Stop hook runs ruff, mypy and pytest after any Python change, which takes about 60 s of CPU and lands in the middle of a timing; do not edit Python files while a benchmark is running, or check afterwards that the spread is not inflated. Adding a test file changes the `tests` workload, so fix the suite before the baseline of `tests`. A command run in the background with its output redirected is block-buffered: the table shows up only at the end. `tools/benchmark.py` sets `SIM_STEPS = 100_000`; with 5000 the simulation took 0.24 s, which a timer cannot separate from noise.
- Profiling and timing (found 2026-10-20, speed-up Phase 1): the `wall` of `tools/benchmark.py` is measured inside the process after the imports (2.24 s once, 0.88 s of it `torch`), so it excludes start-up. `cProfile` does not see MuJoCo's C work behind `MjSpec.attach_body` and `MjSpec.compile`: it reported 11.3 s for an evolution run that takes 16.5 s. Time the phases with `time.perf_counter` around `World.spawn`, `spec.compile()` and the `mj_step` loop instead (scratch scripts, not in the repo). Do not use `spec.copy()` followed by `spec.delete(...)` on a spec that has bodies attached from other specs: it corrupts memory (`malloc(): unaligned tcache chunk detected`, segfault).
- The docs build (`uv run --no-sync sphinx-build -b html docs <dir>`) exits 2 on this machine because the system `pandoc` program is not installed (CI installs it with `apt-get install pandoc`); it needs `sudo`, so the docs group cannot be verified here (Known problems in PLAN.md).
